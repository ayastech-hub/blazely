- [x] **Bot protection: Cloudflare Turnstile + wallet-keyed rate limiting**
  - **Direct answer to "Turnstile vs rate limiting": neither alone is enough, and they solve different problems.** Rate limiting throttles volume but can't tell bot from human and is trivially defeated by rotating IPs. A bot-detection provider (Turnstile) actually distinguishes them, invisibly. Implemented both, layered.
  - **`src/lib/turnstile.js` + `src/components/Turnstile.jsx`** — Cloudflare Turnstile integration (free, invisible for real users). Used the promise-based `execute()` API for the sign-in flow specifically, since that's an imperative effect, not a rendered form.
  - **Wired into the SIWE sign-in** (`WalletContext.jsx` → `siweAuth.js`): a Turnstile token is fetched before every sign-in attempt and passed to Supabase's `/token` endpoint via the documented `gotrue_meta_security.captcha_token` field (confirmed against GoTrue's official REST API docs, not guessed). Requires enabling "CAPTCHA protection" in the Supabase Dashboard with a matching Turnstile secret key — documented in `supabase/README.md`.
  - **New: `supabase/migrations/0003_wallet_rate_limiting.sql`** — rate limiting keyed to the *verified wallet address* (from migration 0001's JWT claim), not IP. This is deliberate: Postgres/RLS has no reliable view of a request's real client IP (it only sees Supabase's connection pooler), so meaningful IP-based limiting belongs at the CDN/edge layer, not in SQL — documented clearly in the README rather than faking IP-awareness Postgres doesn't have. Wallet-based limiting is arguably the stronger signal for this app anyway, since it's tied to the cost of controlling many distinct signed-in identities (each needing its own Turnstile-gated signature), not just rotating a proxy. Applied to comment posting (5 per wallet per 60 seconds) as a Postgres trigger — enforced no matter what calls the table, not just the current frontend code path.
  - **Documented what genuinely can't be done from this codebase**: true IP-based rate limiting/DDoS protection needs Cloudflare (or your host's WAF) sitting in front of the deployed site — an infrastructure/dashboard setup, not a code change. Said so plainly in the README instead of pretending SQL can cover it.
